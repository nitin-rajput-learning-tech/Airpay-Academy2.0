# Product Maturity Audit — 2026-08-04 (7-agent workflow)

**Purpose:** ground the reconciled product roadmap (ADR-028) in the platform's *actual*
maturity, not its plugin count. Four read-only auditors swept the repo in parallel
(enterprise backbone / learner experience / content+AI / decision record), then three
strategist agents worked the combined inventory from the enterprise-buyer,
modern-learner, and platform-architecture lenses.

**Method:** Claude Code Workflow `sentientia-enterprise-strategy` (run `wf_d6ace3b6-a86`,
7 agents, 0 errors). Maturity scale: `production` / `shipped-flag-off` / `mock-mode` /
`scaffold` / `absent`. Every rating is evidence-cited by the auditor; spot-check against
the named files before relying on any single row.

**Headline finding (all three lenses converged):** the platform's problem is not missing
capability — it is *dark* capability. The hardest enterprise engineering (multi-tenancy,
flags, provisioning, privacy, CI/deploy discipline) is production-real, while nearly
everything a buyer or learner would call "modern" is off, mock, local-only, or stubbed.

## Inventory — Enterprise backbone (identity, tenancy, API surface, security/compliance, operability)

The enterprise backbone is strongest where Airpay customer-zero forced it to be real: multi-tenant scoping (BizLMS costcenter + the tenant_identity seam migrated across ~22 caller sites), a mature 5-level feature-flag system with 22 per-plugin registries, HRMS CSV provisioning proven on 2,871 real users, a KeKa joiner/mover/leaver webhook, broad GDPR privacy-provider coverage (38 plugins), and a genuinely disciplined ops layer (10-job CI, typed-confirmation SSH deploy workflow, deploy/cutover/rollback runbooks). Identity is the weakest pillar for a BFSI buyer: login is username/password plus a vendor-inherited OTP form; core Moodle ships auth/oauth2, LDAP and tool_mfa (TOTP/WebAuthn/SMS) but nothing at the product layer configures, documents, or hardens SSO/MFA, Azure AD creds are explicitly "future", and the current theme/sentientia login template has no reCAPTCHA block (the legacy airpayux one did). The public integration surface (local_sentientia_api: 7 REST v1 endpoints + OpenAPI + rate limiter, LTI 1.3 OIDC/JWKS scaffolding with JWT+nonce tests) is well-engineered but feature-flagged default-OFF and never production-exercised; there is no SCIM and no generic outbound webhook subscription for customers. The multi-customer SaaS layer is Phase-0: customer::current() is hardwired to AIRPAY=1, customer-level flag resolution is itself behind a default-OFF flag, and CLAUDE.md's get_customer_branding() does not exist under that name (the real API is customer::branding() with a hardcoded Airpay fallback). Security/compliance is documentation-forward: the trust-track pack (ISO 27001 readiness with 4 open Gap controls including key management and backup procedures, SOC 2 readiness, VAPT program, scale plan) is decision-ready prose with zero executed pen-tests, zero certifications, and scale proof capped at ~3.1k users. Observability exists as code (structured_logger JSON, audit_log whitelist over logstore_standard_log) but wires to Moodle debugging(), not an APM/SIEM. Net: a fintech procurement review would pass tenancy, change management, and privacy design, and fail the questionnaire on SSO/MFA policy, certifications/VAPT evidence, SCIM, and DR attestation.

**Top gaps (most severe first):**

- No production enterprise SSO or MFA policy: no SAML/Azure AD/Entra integration configured (AZURE_* explicitly future), core tool_mfa unconfigured with no policy documentation — fails the first identity section of any BFSI security questionnaire.
- Zero executed security assurance: ISO 27001/SOC 2 docs are readiness roadmaps with 4 open ISO Gap controls (incl. cryptographic key management and backup procedures); the VAPT program has never run — no pen-test report exists to attach to an RFP.
- No SCIM or standards-based provisioning/deprovisioning: lifecycle rests on CSV import plus one beta bearer-token KeKa webhook; no SCIM 2.0 endpoint, no deprovisioning attestation or access-review reporting.
- Multi-customer SaaS layer is Phase-0 in reality: customer id hardwired to Airpay, no customer mapping table (ADR-008 unwritten), customer-level flags behind a default-OFF flag, and the CLAUDE.md-documented get_customer_branding() API does not exist under that name — the white-label multi-customer claim is not demonstrable today.
- Public integration surface is minimal and dormant: 7 REST endpoints (1 write) and LTI 1.3 scaffolding, all default-OFF and never production-exercised; no customer-facing outbound webhooks/event subscriptions at all.
- Observability is not enterprise-grade: structured_logger targets Moodle debugging() (APM integration is a playbook reference only), no SIEM export, no alerting/monitoring stack — the SOC 2 'event logging 7-year retention' claim is asserted, not evidenced by running infrastructure.
- Scale proof capped at ~3.1k users: the 25k/100k/200k load-test tiers and 99.5% availability SLO are unexecuted plans, directly conceding parity to competitors citing 200k-user case studies.
- Backup/DR unattested: rollback runbooks exist but ISO readiness itself flags backup procedures as a Gap, there is no restore-test evidence, and the known empty-filedir clone artifact shows file-content backups are not routinely rehearsed.
- reCAPTCHA absent from the current theme/sentientia login template (present only in the legacy airpayux theme); public-tenant signup bot mitigation rests on a honeypot field.
- Duplicate plugin trees (local/ vs moodle-enhancement/local/) have demonstrably drifted before (sentientia_request stale at v1.2.2; historical F-091/F-092 broken-deploy findings) — a change-management red flag for an auditor assessing build provenance.

## Inventory — Learner & manager experience — modernity vs 2026-class LXP (Degreed / LinkedIn Learning / 360Learning)

The default-on learner journey is a genuinely well-crafted, modern-feeling LMS: split-panel login/signup with live DB hero stats, a first-login onboarding wizard (interests, weekly goals, consent), a role-aware app-shell with persona-specific sidebars (siteadmin/L&D-admin/manager/learner), a rich learner dashboard (KPI tiles, continue-learning rail, urgency-tiered deadlines, activity timeline, gamification points/level/rank/streak widget), a filterable catalog with cart/commerce, and a freshly re-shelled course player with a single TOC sidebar, sticky progress bar, next-activity CTA and keyboard shortcuts. The manager experience is real: team KPIs, compliance drill-down tables, member/performance/allocations pages and CSV export, backed by batched queries. However, everything that would make this a 2026-class LXP rather than a very polished 2020-class LMS — AI skills intelligence, adaptive learning journeys, agentic copilot, talent mobility, real-time leaderboards, live Mentimeter-style sessions, WhatsApp nudges — exists only as alpha/mock-mode plugins behind default-OFF feature flags; "Recommended for You" on the live path is a naive same-category-newest-courses SQL heuristic. Mobile is a substantial but alpha PWA (service worker, VAPID web push, offline page, bottom nav) plus a 3-file Capacitor scaffold; there is no usable native app. Social/community learning is essentially absent (core forums only — no feeds, cohorts, peer sharing, or UGC). Two credibility caveats: the newest, most modern surfaces (app-shell course player, dark tokenization, topbar notifications) are deployed local-only — live airpay.academy has not received the UI wave — and those same new surfaces hardcode English strings (sidebar labels, course-player chrome), regressing the project's own 100%-Hindi-parity policy.

## Strategy lens — Enterprise buyer — the BFSI/fintech CISO security questionnaire, procurement desk, and IT integration review that decide whether Sentientia gets past a first RFP

**Thesis:** A regulated-enterprise buyer never sees your 46 plugins — they see the first three sections of a security questionnaire, and today Sentientia fails all three: identity (no configured SSO, no MFA policy — login is username/password plus an inherited OTP form), assurance (zero executed pen-tests, zero certifications, ISO readiness with open Gap controls on key management and backups), and lifecycle (no SCIM, provisioning by CSV plus one beta webhook). The paradox is that the hardest enterprise engineering — real multi-tenancy, a 5-level flag system, disciplined CI/deploy gates, GDPR/DPDP coverage across 38 plugins — is already at production maturity, while the deal-killers are mostly configuration, execution, and paperwork on scaffolds that already exist (core auth/oauth2 and tool_mfa in-tree, a written and costed VAPT plan, a built-but-dormant REST API). Meanwhile the white-label claim itself is not demonstrable: customer::current() is hardwired to Airpay and there is no customer mapping table, so you cannot even give a prospect a demo tenant. The strategy is therefore not "build more product" — it is a 90-day trust sprint (SSO+MFA, executed VAPT, restore-tested DR, demo Customer-N, procurement pack) followed by SCIM and API activation, with every AI/LXP mock-mode feature sold as roadmap, not capability. Nothing in the flag-off LXP layer wins a BFSI deal; the trust layer loses it.

## Strategy lens — Architecture & sequencing — principal platform architect view: fork→multi-customer SaaS, experience layer, control plane, upgrade economics, AI infra, data spine, extensibility, operability

**Thesis:** Sentientia's binding constraint is not missing architecture — it is that an unusually complete platform is sitting un-shipped and un-proven: the modern UX wave is local-only, every differentiator is a default-OFF mock, customer::current() is hardwired to AIRPAY=1, and AI plumbing is duplicated six times with zero live calls. The strategy is therefore sequencing, not invention: (1) land the built product on customer-zero through the already-designed rollout gate; (2) convert the multi-customer layer from hardcoded constants to data (customer registry + provisioning path) and prove it with a fake Customer N before any sale; (3) consolidate AI onto one gateway riding Moodle's core_ai abstraction and close the two last-mile stubs so an AI artifact can actually land in the LMS; (4) keep the Mustache theme as the web experience for the remaining ADR-018 Moodle window and go headless only where the theme cannot follow — mobile — using the dormant REST API as the forcing function. The overlay upgrade strategy is the economic moat that makes a Moodle fork viable as a product; protect it by driving core-mods toward zero, and do not re-litigate the engine question before the ADR-018 clock demands it.

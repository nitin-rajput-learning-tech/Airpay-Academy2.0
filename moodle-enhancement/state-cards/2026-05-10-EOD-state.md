## Real bugs surfaced + fixed today

### Bug 5: photo.php had `get_area_files` arg order wrong
- **Symptom**: UAT-L1.5 — user could upload a PNG via the browser FP UI,
  click "Save photo", but `user.picture` flag stayed at 0. Page just
  re-rendered with the form.
- **Root cause**: `$fs->get_area_files((int) $data->newpicture, 'user', 'draft', false, '', false)`
  passed the draft *itemid* as first argument, but the signature is
  `get_area_files($contextid, $component, $filearea, $itemid, ...)`.
  File storage looked in the wrong context, found 0 files, the "No file
  selected" error fired silently, user.picture never updated.
- **Fix in `photo.php`**: explicit `$current_user_context = context_user::instance($USER->id)`
  then `get_area_files($current_user_context->id, 'user', 'draft', (int) $data->newpicture, 'id', false)`.
- **Verification**: smoke_photo_upload.php proves the gdlib path
  generates f1.png (100×100) + f2.png (35×35) + f3.png (full size).
  UAT-L1.5.c now passes: post-submit redirects to profile.php with
  "Photo updated." notice, `user.picture: 0 → 315232`.

### Bug 6: Dark-mode SCSS — 6 cascading issues fixed

UAT-L5 had **zero green surfaces** on the first walkthrough. Every Phase-2
page showed 1–3 serious axe violations in dark mode. Root cause was not
one bug but a **cascading set of 6 underlying issues**, each of which
only became visible after the prior one was patched. The full sequence:

**1. Status FG tokens missing (`_tokens-dark.scss`)** — `--ap-color-success`,
`-warning`, `-danger` only had `*-light` overrides; the base colour kept
light-mode `#15803d`/`#a16207`/`#dc2626` which all fail AA on `#1a1d27`.
Fix: add 400-series Tailwind overrides (`#4ade80`, `#fbbf24`, `#f87171`)
to bring all three to ≥4.5:1.

**2. Two parallel CSS variable namespaces (`dark_mode.scss`)** — Phase-2
widgets reference `--ap-text-secondary` (legacy name in `_components.scss`)
while dark mode only overrode `--ap-color-text-secondary` (canonical name
in `_tokens.scss`). Featured-courses widget rendered `#5a6070` on dark bg
= 3.12:1. Fix: add `--ap-text-secondary: #9ca3b4` alongside the canonical
override.

**3. Muted text below AA (`_tokens-dark.scss`)** — `--ap-color-text-muted`
was `#6b7280` which is 3.47:1 on `#1a1d27`. Used on every footer link,
breadcrumb, and "uploaded by" timestamp. Fix: `#9ca3af` (Tailwind gray-400,
5.1:1).

**4. `#region-main` hardcoded white (`dark_mode.scss`)** — Moodle's
standard layout sets `#region-main` background to `#fff` at the layout
PHP level. In dark mode that white panel sat behind dark text on
`/local/airpay_*` pages, and axe walked the ancestor chain to find
effective background = white. Fix: add `#region-main`/`#region-main-box`/
`#page-content` to the dark-mode background override list with `!important`.

**5. Bootstrap utility classes (`dark_mode.scss`)** — `.text-muted`,
`.text-dark`, `.badge.bg-secondary`, table `<td>` and `.text-decoration-none`
all kept Bootstrap's light-mode colours. Fix: explicit dark overrides
mirroring `--ap-color-text-*` for each utility class.

**6. `.alert-info` (`dark_mode.scss`)** — alert-info on `photo.php` and
`import_template.php` shipped Bootstrap's pale-blue light scheme (`#cff4fc`
bg / `#055160` text). Both flagged. Fix: dark blue overrides
(`#172554`/`#c4cad8`/`#1e3a8a`) plus a special-case for the inline `<code>`
tags inside the alert (Moodle `<code style="color:#0a3d62">` would otherwise
stay black on dark blue).

**Why it slipped through earlier**: a11y harness only tested light-mode
viewport. UAT-L5 is the first thing that walked dark-mode rendering with
axe-core — and axe-core walks the entire ancestor chain for effective
background, which is the only way these 6 problems surface together.

### Harnesses
- `uat_l_uploads.mjs` — drives Moodle's `/repository/repository_ajax.php`
  API directly (same pipeline as the FP YUI module uses) for all 5 file-
  upload surfaces. Extracts draftitemid from the form's hidden input,
  POSTs the file to the upload repository (`repo_id=5` on this install,
  type='upload'), then submits the parent form and grep's the result for
  the expected summary text.
- `uat_l_ics_clients.mjs` — fetches `ics.php`, parses with **ical.js**
  (Mozilla's reference parser, same engine Calendar Server uses → same
  parsing rules as Outlook/Apple/Google clients). Validates RFC 5545
  structure: CRLF endings, ≤75-octet line folding, VCALENDAR/VEVENT/
  required properties, DTSTART/DTEND in UTC, UID format, STATUS=CONFIRMED,
  TZID/VTIMEZONE pairing.
- `cli/uat_l_messaging.php` — server-side smoke for `mdl_notifications`
  pipeline. Triggers `notify_requester_of_decision`, `notify_assignee_of_allocation`,
  and `test_send`; asserts each lands in `mdl_notifications` with the
  expected component+eventtype.
- `uat_l_mobile_darkmode_svg.mjs` — three checks bundled:
  - **Mobile**: re-runs axe a11y at 590px viewport across all Phase-2
    surfaces (9 surfaces).
  - **Dark mode**: toggles `html[data-theme=dark]` +
    `html.dark-mode` + `body.dark-mode` + `body.ap-dark` (matches the
    real dashboard.mustache toggle exactly — earlier attempts used
    `data-bs-theme` only which failed to fire `[data-theme="dark"]`
    selectors in `_tokens-dark.scss`).
  - **Radar SVG**: inspects `<title>` + `<desc>` on the radar SVG —
    screen readers (VoiceOver, NVDA, JAWS) read these to announce the
    chart. Validates static structure since I can't drive real SR
    on Windows headless.

## Caveats and what's still out of scope

What automated UAT can't simulate (genuinely needs a human or external infra):

- **Real Outlook / Apple Calendar / Google Calendar import**: ical.js
  parsing is the most rigorous static check possible, but ultimately
  what matters is that the user gets the meeting invite in their actual
  calendar app. RFC 5545 compliance is necessary but not sufficient
  (e.g. some Outlook versions are quirky about CN= parameters).
- **Real SMTP delivery**: noemailever blocks actual email send. We
  verified `mdl_notifications` rows are created, which is what the
  message bus does locally. SMTP delivery on production needs to be
  verified separately.
- **Real screen reader testing on macOS/Windows**: VoiceOver, NVDA,
  JAWS each have quirks. Static SVG `<title>`/`<desc>` analysis is
  the static-side guarantee but cross-SR real-time announcement is
  a manual check.
- **Browser cross-compat**: Playwright runs real Chrome on Windows.
  Safari (macOS+iOS), Firefox, Edge variations need separate runs.

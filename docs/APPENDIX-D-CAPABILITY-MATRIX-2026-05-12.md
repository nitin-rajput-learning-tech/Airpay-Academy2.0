## Capabilities × tenancy concerns

The Phase 8 audit highlighted that **system-context capabilities require an additional tenant-equality check** at the application layer. The architecture documented in Section 1.2 of the master document layers three defences:

1. **Capability check** at the appropriate context level (above).
2. **Role assignment** at tenant root category — managers in tenant `/77` only hold their role at category context `/77`, so capabilities held at `CONTEXT_COURSECAT` automatically scope correctly through Moodle's role-context inheritance.
3. **Application-layer tenant equality** via `\local_airpay_core\tenant::require_access()` for any system-context capability that touches user-scoped data.

The capabilities most at risk if any single defence fails:

| Capability | Tenant risk if unscoped | Mitigation status |
|---|---|---|
| `local/airpay_cart:viewallorders` | View other tenants' orders | Phase 8.1 B1 ✓ |
| `local/airpay_cart:refund` | Refund other tenants' orders | Phase 8.1 B1 ✓ |
| `local/airpay_cart:manageprices` | Re-price other tenants' courses | Phase 8.1 B9 — moved to CONTEXT_COURSE ✓ |
| `local/airpay_proctoring:review` | Review other tenants' recordings | Phase 8.1 B2 ✓ |
| `local/airpay_proctoring:viewattempts` | List other tenants' attempts | Phase 8.1 B2 ✓ |
| `local/airpay_request:overrideroute` | Approve requests in other tenants | Phase 8.1 B10 ✓ |
| `local/airpay_recompletion:reset` | Reset other tenants' completions | Phase 8.1 B6 ✓ |
| `local/airpay_org:manage_multiorganizations` | Edit other tenants' org tree | Audited in pre-Phase-8 review |
| `local/airpay_emails:manage_rules` | Send to other tenants' users | Rule-level tenant scoping |
| `local/airpay_notifications:manage` | Define rules affecting other tenants | Rule-level tenant scoping |

Total Airpay-owned capabilities: approximately **82 distinct capability rows** across 21 plugins, plus the inherited Moodle core capabilities used by airpay plugins (`moodle/site:config`, `moodle/role:manage`, etc.).

## Default archetype grants summary

| Archetype | Plugins where archetype gets at least one CAP_ALLOW |
|---|---|
| `user` | cart (view/purchase), challenge (participate), privacy (dsr_act), request (request) |
| `student` | cart (view/purchase), challenge (participate), proctoring (attempt), evaluation (respond) |
| `editingteacher` | cart (manageprices via course context), classroom (manage), courses (update) |
| `teacher` | cart (view), courses (view) |
| `manager` | every plugin's view/manage caps + cart admin caps + proctoring review + recompletion manage + request approve |
| `trainer` | classroom (attendance, view) |
| `siteadmin` | bypasses the capability system; implicit grant on everything |

Custom roles `employee` and `administrator` get explicit grants via each plugin's `db/install.php` hook. The grants are documented per-plugin in the install.php files and audited under `moodle-enhancement/ACCESS-MATRIX.md`.

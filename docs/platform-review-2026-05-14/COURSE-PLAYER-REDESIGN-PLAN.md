# Course Player — Redesign Plan

**Surface:** `/course/view.php?id=N` (every course view + every SCORM/quiz/activity launch)
**Status:** EXISTS · **Priority:** P0 (#3 on the 7-redesign list) · **Effort:** L (8-12 sessions)
**Theme layout:** `theme/airpayux/layout/course.php` (226 lines)
**Theme template:** `theme/airpayux/templates/course.mustache` (298 lines)
**SCSS:** `theme/airpayux/scss/moodle/partials/_surface-course.scss` (651 lines, **98 hex literals**)
**SCSS (player):** `theme/airpayux/scss/moodle/partials/_course-player.scss` (278 lines, **36 hex literals**)

---

## 0. Why this is #3 (and why it's the hardest)

The Course Player is **where the actual learning happens**. Every SCORM module, every quiz attempt, every video, every assignment lives inside `/course/view.php?id=N`. Per Moodle's analytics it's the highest-time-on-page surface in any LMS — average learner spends 4-8× more time here than on the catalog or dashboard.

It's also **the deepest scope of any P0 redesign**:

1. **Moodle owns most of the markup** — the course content, activity links, completion icons, gradebook integration, breadcrumbs — all rendered by Moodle core or by activity plugins (mod_scorm, mod_quiz, mod_assign, mod_resource, mod_page, mod_url, etc.). We can theme-override via `templates/core_courseformat/*` but the data shapes are fixed.

2. **134 hex literals across 929 lines** — almost as much legacy CSS as the entire dashboard had pre-redesign. Migration is mechanical but high-volume.

3. **High regression risk** — this is where learners spend most of their time. A visual regression here is more visible than a regression anywhere else.

4. **Multi-device** — same surface needs to work on phone (one-handed in a meeting), tablet (50% split-view per manifesto §8), laptop (focused study), and pinned-tab desktop (background while working). Each device class wants a different layout density.

## 1. Current state

### What we own (theme overrides)

- `layout/course.php` — sets up `$courseindexopen` / `$blockdraweropen` drawer state, builds the template context including primary nav, secondary nav, region-main settings menu, blocks, breadcrumbs
- `templates/course.mustache` — the outer shell that renders all of the above + the activity content
- `templates/course_context_header.mustache` + `course_full_header.mustache` — variants of the course header
- `templates/core_courseformat/local/courseindex/course_drawer_header.mustache` — the side-drawer header
- `_surface-course.scss` (651 lines) — visual treatment for the player surface
- `_course-player.scss` (278 lines) — variant CSS specific to certain layouts

### What Moodle owns (out of scope unless we override)

- Activity completion tick boxes (`mod/scorm/lib.php` etc.)
- Gradebook column rendering (`grade/report/*`)
- Activity content itself (SCORM iframe, quiz HTML, assignment submission UI)
- Forum threads, glossary entries, wiki pages — each module's own renderer
- The "course management" admin overlay (when teacher role is editing)

We can theme-override individual core templates by placing a custom version in `theme/airpayux/templates/core_courseformat/...` — Moodle picks the theme version first. This is the canonical extension point.

### What's wrong today

Same diagnosis as the dashboard before redesign:
1. **134 hex literals** — tenant branding doesn't propagate cleanly, dark mode requires manual override rules per selector
2. **Drawer widths are hard-coded** — `360px` left drawer (course index) + `400px` right drawer (blocks). On a 1280px laptop, that's 760px of chrome leaving 520px for content. On iPad in split-view (50% of 820px = 410px viewport), both drawers collapse but the breakpoint is at the wrong place.
3. **The right-side block drawer is largely empty** for most courses — it's where the legacy BizLMS blocks went, but most have been deprecated. Modern Moodle courses don't put much in the right drawer.
4. **Activity completion icons inconsistent** — some use Moodle defaults, some use custom `airpayux` overrides, some inline `<i class="fa">` icons. No unified system.
5. **Mobile experience** — drawers collapse to bottom sheets via the existing `drawers.js`, but the content area doesn't reflow nicely. Course content is generated by activity plugins, not the theme, so we can't easily restructure it.

---

## 2. Redesign principles (manifesto applied)

1. **Mobile is the canonical surface** (§1.1) — the player is the highest-mobile-traffic surface in the LMS. Pull-to-refresh, swipe-between-activities, bottom-bar nav need first-class treatment.
2. **Touch-first** (§1.2) — every activity link, every completion checkbox, every quiz answer must be ≥44pt. Moodle defaults often miss this.
3. **Content is the interface** (§1.3) — the chrome (drawers, blocks, breadcrumbs) should collapse aggressively when the learner is mid-activity. Reading flow trumps navigation.
4. **Motion is meaning** (§1.4) — drawer slide-in/out, activity completion checkmark animation, progress-bar fill, page-transition crossfade — all need tokens-aware durations.
5. **Empty states are scenes** (§1.5) — when a learner opens a course with no enrolled activities (rare but happens for catalog-browsing learners), the empty state should invite enrolment, not show a blank section list.

## 3. The iterations

### Iter 1 — Tokens migration (foundation, low risk)

Migrate `_surface-course.scss` + `_course-player.scss` to use `--ap-*` tokens. **134 hex literals → 0.** Same visual treatment as today — pure token swap. Same pattern as catalog iter 1.

Risk: low. Zero visual change. Dark mode auto-flips via the global `body.dark-mode` token remap, removing most per-rule dark overrides.

Estimated: 1 session.

### Iter 2 — Course header polish

The course header has three variants (`course.mustache`, `course_context_header.mustache`, `course_full_header.mustache`). Each was added at different points; styling diverges. Consolidate into one canonical header with optional banner image, breadcrumb, title, and quick-actions.

The data layer already provides `headercontent`, `courseimage` (when available), `progress_pct` (for enrolled courses).

Estimated: 1-2 sessions.

### Iter 3 — Drawer responsive overhaul

The left drawer (course index) is the most-used drawer. Make it:
- 280px on laptop+ (was 360 — narrower so more space for content)
- Bottom-sheet on mobile (already does this; tighten the slide animation)
- Auto-collapse on tablet 50% split-view (currently stays open, eats half the viewport)
- Sticky table-of-contents pattern — section titles always visible, items within sections scroll

The right drawer (blocks) — most courses don't need it. Make it opt-in per course rather than always-present.

Estimated: 2 sessions. **Med risk** — visible on every course page.

### Iter 4 — Activity row polish

Every activity link in the course index is a `<li>` with an icon, name, completion state, and (sometimes) due date. Standardise:
- Icon size 24×24 from tokens
- Completion state: `.airpay-activity-row--complete / --in-progress / --not-started / --overdue` with semantic tints (same vocabulary as dashboard/catalog)
- Tap target 44pt min
- Right-aligned completion checkmark (was inline with name — visually noisy)

Estimated: 2 sessions.

### Iter 5 — Mobile bottom-nav

On mobile, replace the top-bar primary nav + drawer with a fixed bottom nav: ⌂ Home · 📖 Continue · 🔍 Search · 👤 Me. The activity within the course gets full-screen treatment without the drawer eating viewport.

This is a bigger structural change — manifesto §4.1 spec. **Med-high risk** because it's the most-visible structural change in the player.

Estimated: 2 sessions.

### Iter 6 — Activity transitions

When a learner finishes activity A and clicks activity B, the page should NOT do a full reload. Use Moodle 5's native `core/router` or a custom drop-in that fetches just the activity content (SCORM iframe stays, surrounding chrome stays). Manifesto §5.3 — "crossfade · default + ease-in-out" for activity transitions.

**High risk** — touching navigation behavior. Probably wait until later iters to validate the simpler stuff first.

Estimated: 2-3 sessions.

### Iter 7 — Empty + edge states

- Course with no enrolled sections — invite to enrol in the parent program
- Course end-date passed — show "This course closed on X" + link to history
- Course locked by prerequisites — show "Complete Y first to unlock this"
- SCORM module failed to load — friendly error + "Try again" + "Report problem" CTA

Estimated: 1 session.

---

## 4. What we're NOT changing

- Moodle's data model (course, course_sections, course_modules, etc.)
- Activity plugin renderers (`mod_scorm/view.php`, `mod_quiz/view.php`) — these are core, untouched
- Gradebook columns
- Backup/restore behaviour
- Course-completion rules engine
- Enrolment methods
- Blocks system (we may DEDUCE the right drawer should be opt-in, but blocks themselves stay)

---

## 5. Risk register

| Iter | Risk level | Why |
|---|---|---|
| 1 — Tokens | Low | Pure CSS swap, visual diff should be near-zero |
| 2 — Header polish | Low-Med | Visible on every course page but contained markup |
| 3 — Drawer responsive | Med | Drawer behaviour affects every interaction |
| 4 — Activity row | Med | Most-used element in the player |
| 5 — Mobile bottom-nav | Med-High | Structural change to primary navigation pattern |
| 6 — Activity transitions | High | Touching navigation; rollback path needs care |
| 7 — Empty states | Low | Adds content, doesn't remove |
